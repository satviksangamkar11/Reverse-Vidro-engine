## For the CODER (Nemotron)
- Standard library only, Python 3.14. No network, no model calls, no GranthStudio import, no absolute drive paths in modules (roots are parameters).
- The evidence folder is READ-ONLY: open files for reading only, never write, move or delete there. Outputs go only to the out_dir the caller passes.
- Never write the 7-letter name of the 3D tool in any file, comment or docstring. The report key `potential_<tool>_implementation` is built as `"potential_" + "blend" + "er_implementation"`.
- Real data (verified): descriptive report fields can be str, list, dict or None; only video_id/scene_id (str), start_frame/end_frame (int), start_time/end_time (number), evidence_frames (list of int), granthstudio_capability (str) are type-checked. Folders without `api_log.json` are skipped. Relative paths in outputs use forward slashes.
- Tests: synthetic tmp dirs; tests are frozen once written; a failing test means fix the module, never weaken the test. Reply ONLY with the fenced FILE blocks the spec asks for.

- REPLY PARSER TRAP: the loop parses your reply with a regex for lines that START with `FILE:` followed by a fenced block. NEVER let a line of your code or test source start with `FILE:` (or contain a raw triple-backtick fence line) when it lands in the reply. When a test needs sample spec text with FILE blocks, build the lines by concatenation inside the string, for example `"FIL" + "E: pieces/x.py"` and a fence made as `"`" * 3`, never as literal lines. Round 0 of the p1_specdraft job failed exactly this way (phantom files foo.py and bar.py).

## Flow rules (owner 2026-10-29)
- AUTO-ADVANCE: when a step passes (tests pass, and its one review says PASS or has no HIGH/MED), the next step starts by itself; nobody waits for a human between passing steps. Any failure, escalation or non-PASS review STOPS the chain with a recorded reason (never skip, never continue past a failure).
- REVIEW EVERY APPLIED CHANGE: each change the supervisor applies (spec amendment, tool or script edit, rule or doc edit) is reviewed read-only by a reviewer (Luna) before it counts; HIGH/MED findings are fixed and recorded as a decision. Supervisor changes also go through the loop: code is written by Nemotron, never by hand.

## Luna reviewer tooling (lesson 2026-10-29)
Luna is fast (seconds to a minute). Luna also runs shell commands in the repo (rg, Get-Content) to open files it was told about. If the caller collects output through PIPES, those helper processes keep the pipes open and the caller waits until its timeout although Luna has finished (three false "hangs" of 35, 26 and 5 minutes). ALWAYS run Luna with output going to FILES (`codex exec ... -o <last-message file>`, stdout/stderr to a file); never `capture_output=True`. `tools/codex_review.py` and `tools/codex_change_review.py` do this; a timeout writes a visible NO_REVIEW file. The review tools never create folders.
- WINDOWS BYTE-RANGE LOCKS (P1-D10): lock a single byte at offset 2**30 (far beyond the end of any file content), never a byte that holds content; any OSError from a lock attempt or from opening a locked claim file means "claimed" and must become a normal conflict result, not a crash.

- STOPPING A LOOP (P1-D14): Stop-Process or `os._exit` skips the loop's restore step. Files written by earlier rounds stay and no ESCALATE.md is written. After a forced stop, wipe `_loop/<job>` and the job's piece files (or restore them) before relaunching.
- KEY RULE IN THE REAL POOL (P1-D14, narrowed by P1-D16): our copy of `KeyPool` cools a key for one window after ANY failed request, but `chat_stream` only SWITCHES key for transient failures (see KEY RETRY POLICY); 401/402/403 retire the key.
- STOPPING A LOOP, FULL RULE (P1-D16): a forced stop, a crash or Ctrl+C all skip the loop's restore step and write no ESCALATE.md; wipe `_loop/<job>` and the job's piece files (or restore them) before relaunching. The launcher exits 4 on a claim conflict (3 is the loop's escalate code).
- KEY RETRY POLICY (P1-D16): `chat_stream` switches key only for 401/402/403, 429, 5xx and transport failures (status 0 without a finish value); an incomplete 200 stream (finish=length, content_filter, none) or any other 4xx returns at once and does not cool the key. Never retry a reply that would fail the same on every key.

## KNOWN CODER TRAPS (P1-D33): every one of these happened; the checks in `pieces/test_guards.py` and the reviewers look for them
1. NEVER `raise X` inside a `try:` whose `except` catches X (or Exception): the raise is swallowed and the guard silently does nothing (happened twice: "refuse a folder inside the evidence folder"). Compute the condition first, raise outside the `try`.
2. A requirement that says "set / call / write X" must be done IN THE CODE and tested (the audio module only had a COMMENT about HF_HUB_OFFLINE, so a model download was possible). A comment is not an implementation.
3. PRODUCER -> CONSUMER SHAPES: read the exact keys of the dict you consume from the producing module's code or the spec; never invent a nested shape. Tests must build inputs with the producer's REAL output or the documented keys, never a shape you made up (the beats module read `audio["transcript"]["text"]` while the audio module writes `transcript_text`).
4. Expected values in tests come from the spec's rule, computed by the rule, not by hand (wrong hand-computed order, wrong rounding list, a limit exactly at the length).
5. In a fix round return EVERY file of the job in full; an omitted unchanged file is kept, but a cut-off block is lost. Never leave a code fence open.
6. Tests must not leak: no environment variable, working directory or global left changed, no file written outside tmp folders, no test that waits on a real clock or a real model.
7. No absolute drive paths in modules; never create folders; never write inside the evidence folder; stdlib plus the imports the spec allows.
- Real record fields (for example `potential_` + the 3D tool name + `_implementation`) contain the forbidden 7-letter name: never type that key literally in a synthetic record; build it by string concatenation ("potential_" + "blend" + "er_implementation") or leave it out (found 2026-10-30, a job was refused four rounds in a row).
