# SPEC P_CHAIN: NEW `pieces/p1_chain.py` + NEW `pieces/test_p1_chain.py` (auto-advance driver: when a step passes, the next step starts by itself)

GOAL (owner rule 2026-10-29): a chain of prepared steps runs one after another WITHOUT a human between passing steps. A step that passes (job: tests passed; and its one review says PASS or has no HIGH/MED line) starts the next step. ANY failure, escalation, timeout or non-PASS review STOPS the chain with a recorded reason; the chain never skips a step and never continues past a failure. The driver itself makes NO model call and NO network call: it only launches local processes through injectable functions.

REAL FACTS (verified in this repo):
- A job is a JSON file like `_loop/jobs/p1_inventory.json` with a `name`. It runs as: `python scripts/source/fix_loop.py --job <job.json> --root .` (cwd = repo root, `sys.executable`). `--dry-run` validates a job without calling any model and exits 0 when valid.
- While and after it runs the loop writes `_loop/<name>/status.json` (JSON with `"state"`, `"round"`, `"tests_passed"`). `state` is one of `running`, `passed`, `passed-no-review`, `escalate`. `passed` and `passed-no-review` mean success; `escalate` means failure. The status file may not exist for the first minutes after launch.
- Only ONE fix_loop process may run at a time.
- A review is run as `python tools/codex_review.py <spec> <module> <test>`; it writes `work/phase1/reviews/<module stem>.review.md`. The file starts with a header line, then a blank line, then the body. The review PASSES when the body (text after the first blank line) starts with `PASS` (case-insensitive) OR (the body is NOT empty AND contains no line that starts with `HIGH` or `MED`). An empty or whitespace-only body ALWAYS FAILS. Otherwise it FAILS.

CHAIN FILE (JSON): `{"name": str, "steps": [step, ...]}`. A step is `{"id": str, "type": "job" | "command", ...}`.
- type `job`: `"job"` (path of the job JSON, str), optional `"guard"` (list of str), optional `"review"`: `{"spec": str, "module": str, "test": str}` (paths relative to the repo), optional `"timeout_s"` (number, default 3600).
- type `command`: `"argv"` (non-empty list of str), optional `"timeout_s"` (default 600), optional `"judge"` (path of a review file, relative to the repo). Exit code 0 = success; when `judge` is present the file is read AFTER a successful exit and must pass `judge_review`, else the step is STOPPED with reason `review not PASS`. This is how a spec or change review (`python tools/codex_change_review.py ...`) gates the next step.
- type `draft` (prepares one automatic spec drafting; makes no model call): `"spec_id"` (str), `"brief"` (path of a text file with the step's goal, relative to the repo), `"probe"` (list of str paths of the real input data to profile). It calls the injectable `prepare_draft(spec_id, brief_text, probe_paths) -> str` (default: imports `make_draft_job` from the module `p1_specdraft` located in the same folder as this file, via `sys.path`, and calls it with `repo`) and stores the returned job path. A `draft` step is followed in the chain by an ordinary `job` step that runs `_loop/jobs/draft_<spec_id>.json`. Missing brief file or an exception from `prepare_draft` -> STOPPED with the error text.
- Every `job` step may also have `"guard"`: a list of repo-relative file paths. Before launching, record `file_sha256` of each (a missing file is recorded as null); after the job succeeds, every guarded file must have the same hash, else STOPPED with reason `guarded file changed: <path>`. (Used to keep the shared spec lint test unchanged by a drafting job.) Compute hashes with `hashlib` inside this module.
`load_chain(path)` returns the parsed dict, or raises `ValueError` naming the problem for: unreadable or invalid JSON, missing/empty `name`, `steps` not a non-empty list, duplicate `id`, unknown `type`, a job step without a str `job`, a command step whose `argv` is not a non-empty list of str, a `review` that lacks one of its three str keys.

STATE FILE: `<repo>/_loop/<chain name>.chain.json` (a file inside the existing `_loop` folder; never create folders). Content: `{"name", "updated" (ISO UTC), "stopped_at": step id or null, "steps": {id: {"status": "PENDING"|"RUNNING"|"DONE"|"STOPPED", "reason": str|null, "started": iso|null, "finished": iso|null}}}`. Write it atomically (temp file in the same folder, then `os.replace`) after EVERY status change. On start, load an existing state file; steps already DONE are skipped (resume); STOPPED or RUNNING steps are restarted from scratch.

FUNCTIONS (public):
1. `load_chain(path) -> dict`.
2. `run_chain(chain, repo, deps=None) -> dict` returning `{"completed": bool, "stopped_at": str|None, "reason": str|None, "done": [ids in order]}`. `repo` is a path (str or Path). `deps` is an optional dict of injectable functions that override the defaults (so tests never start real processes):
   - `loop_running() -> bool`: default asks PowerShell: `powershell -NoProfile -Command "(Get-CimInstance Win32_Process -Filter \"name='python.exe'\" | Where-Object { $_.CommandLine -like '*fix_loop*' } | Measure-Object).Count"` and returns True when the printed number is greater than 0 (any error -> False).
   - `dry_run(job_path) -> int`: default runs `fix_loop.py --job <job> --root . --dry-run`, returns the exit code.
   - `launch(job_path) -> None`: default starts the loop with `subprocess.Popen` (detached, cwd = repo, stdout/stderr appended to `_loop/<job name>.run.log`).
   - `read_status(job_name) -> dict | None`: default reads `_loop/<job name>/status.json`, returns None when missing or unreadable (never raises).
   - `review(step) -> str`: default runs the review command with `subprocess.run` and returns the text of the review file it wrote.
   - `run_cmd(argv) -> int`: default `subprocess.run(argv, cwd=repo).returncode`.
   - `sleep(seconds)`, `now() -> float` (monotonic seconds), `poll_s` default 15.
   JOB STEP LOGIC, in order: (a) if `loop_running()` is True -> STOPPED, reason `another fix_loop is running`; (b) `dry_run` must return 0 else STOPPED `dry run failed`; (c) `launch`; (d) poll `read_status(name)` every `poll_s` until `state` is `passed` or `passed-no-review` (success), `escalate` (STOPPED, reason `escalated`), or the timeout passes (STOPPED, reason `timeout`); if the status says `running` or is missing but `loop_running()` is False for two consecutive polls after the first poll, STOPPED with reason `loop process ended without a final state`; (e) on success and when the step has a `review`, call `review(step)`; judge it with the PASS rule above; a failing review -> STOPPED, reason `review not PASS`, keeping the review text's first 300 chars in `reason`; (f) otherwise DONE.
   COMMAND STEP LOGIC: `run_cmd(argv)`; non-zero -> STOPPED with reason `exit code N`; zero and a `judge` file -> read it (`read_text(path) -> str` injectable, default reads the file, missing file -> STOPPED `judge file missing`) and apply `judge_review`; a failing verdict -> STOPPED `review not PASS` with the first 300 chars; otherwise DONE.
   DRAFT STEP LOGIC: read the brief (injectable `read_text`), call `prepare_draft`, mark DONE (the job path is stored in the step's `reason` field as `job=<path>`).
   GUARD LOGIC for job steps: described above; compare hashes through the injectable `file_hash(path) -> str|None` (default: SHA-256 of the file, None if missing).
   The job name comes from the job JSON's `name` (read it from `repo/<job path>`; unreadable -> STOPPED `bad job file`).
3. `judge_review(text) -> bool`: the PASS rule above (pure function; tested on its own).
4. `main(argv) -> int`: `python pieces/p1_chain.py <chain.json> [repo]`; repo defaults to the current directory; prints ONE line `chain <name>: completed|stopped at <id>: <reason>`; returns 0 when completed else 1. Guard with `if __name__ == "__main__": raise SystemExit(main(sys.argv[1:]))`.

TESTS (pytest; tmp dirs and fake `deps` only; NO real process, NO network, NO model call): all steps pass -> completed True, `done` in order, state file shows every step DONE; a job whose status turns `escalate` -> stopped_at that id and LATER steps stay PENDING and are never launched; a failing review (a `HIGH - ...` line) -> stopped with reason starting `review not PASS`; a PASS review and a review with only LOW lines both advance; `judge_review` unit cases (PASS, `pass`, header-less text, HIGH line, MED line, LOW only, empty string -> True only when it has no HIGH/MED line and is not empty, empty -> False); resume: a state file with step 1 DONE makes the driver skip step 1 (its launch is not called); `loop_running()` True -> stopped with `another fix_loop is running` and nothing launched; dry run non-zero -> stopped; a command step with exit code 3 stops with `exit code 3`; a command step with `judge` whose review text has a `HIGH - x` line stops with `review not PASS`, and with `PASS` advances; a `draft` step calls `prepare_draft` once with the spec id and the brief text and is DONE, an exception from it stops the chain; a guarded file whose hash changes during a job step stops with `guarded file changed`, an unchanged one does not; `load_chain` accepts a `draft` step and rejects one without `spec_id`, `brief` or a list `probe`; timeout -> stopped with `timeout` (use a fake `now` that jumps); a missing status for polls plus `loop_running()` False twice -> `loop process ended without a final state`; `load_chain` raises ValueError for each invalid case listed above; the state file is valid JSON after every run.
